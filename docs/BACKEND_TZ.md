# ТЗ для backend-разработчика — HomeFold

Версия документа: 1.0 · 26.10.2026 · Аудитория: backend-разработчик, который подключается к проекту.

## 0. Коротко

**HomeFold** (в коде и репозитории пока «Ryadom») — семейный органайзер для iOS: общие списки покупок, дела с повторами и напоминаниями, защищённые документы, обзор. Приложение **offline-first**: UI читает локальную базу (SwiftData), все изменения кладутся в очередь и уходят на сервер.

Backend **уже написан** (NestJS + PostgreSQL + Prisma, 98 тестов, контракт в [API.md](API.md), схема в `backend/openapi.json`). iOS-клиент **ещё не подключён** к сети: нет сетевого слоя, входа, синхронизации. Пока клиент писался, накопились требования, которых в бэкенде нет, и расхождения в контракте.

**Задача этого ТЗ:** довести backend до состояния, с которым iOS-клиент можно подключать без обходных путей, и подготовить его к выпуску в App Store.

Приоритеты: **P0** — без этого клиент нельзя подключить или выпустить; **P1** — нужно к релизу; **P2** — после релиза. Размер: S — до дня, M — 2–3 дня, L — неделя и больше.

### Что НЕ нужно менять
Контракт из [API.md](API.md) остаётся эталоном: идентификаторы создаёт клиент, `PUT` — upsert, `/sync/push` идемпотентен по `opId`, удаление приоритетнее правки, курсорный `/sync/pull`, WebSocket как сигнал. Расхождения в названиях полей решает клиент (см. раздел 2.9), на сервере меняем только то, что перечислено ниже.

## 1. Что уже есть (проверять не нужно, но знать полезно)

Вход по email-коду (JWT 15 мин + ротация refresh), семья и роли, приглашения (токен 7 дней, лимит с учётом ожидающих), покупки, дела с сериями и материализацией на 60 дней, документы с прямой загрузкой в хранилище и подтверждением, `/sync/push` и `/sync/pull`, WebSocket-сигнал, push (APNs) при назначении дела или покупки, подписки (StoreKit 2: `verify`, `restore`, вебхук Apple), лимиты free/Plus, `DELETE /account`.

## 2. Работы

### 2.1 [P0, M] Детерминированные идентификаторы выполнений серии

**Проблема.** Клиент создаёт повторяющееся дело офлайн и сразу строит выполнения на 60 дней вперёд. Идентификатор выполнения он вычисляет сам, чтобы два устройства (и сервер) получили один и тот же id для одной даты. Сервер сейчас выдаёт случайные id при материализации, плюс есть `@@unique([seriesId, originalDate])`. В итоге — конфликт по уникальности или дубли.

**Требование.** Сервер материализует выполнения с теми же идентификаторами:

- `occurrenceId = UUIDv5(namespace = seriesId, name = "YYYY-MM-DD")`, где дата — `originalDate` по правилу серии в локальной дате семьи (`timezone` серии);
- `checklistItemId (шаблон) = UUIDv5(namespace = occurrenceId, name = "chk-<индекс с нуля>")`;
- UUIDv5 по RFC 4122: `SHA-1(байты namespace ‖ UTF-8 name)`, первые 16 байт, версия 5, вариант RFC. В Node — `uuid.v5(name, namespace)`.

Тестовый вектор (проверен независимой реализацией):

| namespace | name | результат |
|---|---|---|
| `11111111-2222-3333-4444-555555555555` | `2026-10-26` | `fba2510a-43b5-5a39-9484-6b27831b9285` |
| `fba2510a-43b5-5a39-9484-6b27831b9285` | `chk-0` | `1f97920e-e957-587f-8b07-ac703e321726` |

Дополнительно:
- Если клиент прислал выполнение с `(seriesId, originalDate)`, которое уже есть на сервере, — **не ошибка 500**, а обычный upsert по id (id совпадут). Если не совпали (старые данные) — вернуть `rejected` с кодом `CONFLICT_OCCURRENCE` и актуальной записью.
- Удалённое выполнение серии не воскрешать при повторной материализации (клиент ведёт себя так же).

**Приёмка:** тест «два клиента и сервер материализуют одну серию — в базе ровно одно выполнение на дату»; тест на тестовый вектор.

### 2.2 [P0, S] Разовое дело = серия с `repeat: none` не должно требовать Plus

**Проблема.** `TasksService.upsertSeries` вызывает `requireRecurring` для любой серии. Клиент создаёт серию даже для разового дела (`recurrence: "none"`), поэтому бесплатный пользователь не сможет создать ни одного дела через `/sync/push`.

**Требование.** `PREMIUM_REQUIRED (feature: recurring_tasks)` только если `repeat != none`. Серия с `none` разрешена на free; при создании по умолчанию `repeat` = `none`, а не `daily` (сейчас `daily`). Материализация для `none` — одно выполнение на `startDate`.

**Приёмка:** free-семья создаёт серию с `repeat: none` — `applied`; с `daily` — `rejected PREMIUM_REQUIRED`.

### 2.3 [P0, S] Поле `tag` у дел

Клиент хранит метку дела (в интерфейсе: «Дети», «Дом», «Документы», «Здоровье», «Работа», либо пусто). Нужно:
- `tag String? (≤ 24 символа)` в `TaskSeries` и `TaskOccurrence`, в DTO upsert, в ответах `GET /tasks`, `pull`;
- значение произвольное (список меток клиентский и может расширяться); пустая строка и `null` равнозначны;
- при материализации выполнение наследует `tag` серии; правка серии обновляет `tag` невыполненных и не правленных вручную.

### 2.4 [P0, M] Создание семьи и приглашения под офлайн-клиента

**Семья.** Клиент создаёт семью локально (id уже раздан всем локальным записям) и потом отправляет её на сервер.
- `POST /families {id?, name, displayName}` — необязательный клиентский `id`; повтор с тем же `id` от того же пользователя идемпотентен (200 с той же семьёй), а не `ALREADY_IN_FAMILY`.

**Приглашения.** Администратор вводит имя приглашаемого и видит его в списке участников как «ждёт подтверждения».
- `POST /invitations {id, displayName}` — клиентский `id` (идемпотентность) и имя приглашённого (1–40 символов). Сейчас тело пустое.
- `GET /invitations` возвращает `displayName`.
- Токен виден один раз. Если ответ на создание потерян (офлайн-повтор), клиент не знает ссылки. Поэтому: повтор `POST` с тем же `id` → 200 **без** `token`/`url` и с признаком `tokenIssued: false`; плюс `POST /invitations/{id}/reissue` → новый токен и `url`, старый токен инвалидируется (срок 7 дней считается заново).
- При принятии приглашения: создаётся участник, запись `Change` для сущности `family` (клиент перечитает `GET /families/me`), приглашение закрывается. В ответе `GET /families/me` участник приходит с идентификатором пользователя; клиент заменит им локальную запись «ожидает».
- Лимит участников уже считает ожидающие приглашения (`members + pending`) — **подтвердить тестом**, клиент ждёт именно такого поведения.

### 2.5 [P0, M] Ссылки-приглашения (Universal Links)

`INVITE_BASE_URL` сейчас `https://ryadom.app/join`. Нужно:
- решить домен продукта (см. вопросы, раздел 4) и прописать его;
- отдавать `/.well-known/apple-app-site-association` (без расширения, `Content-Type: application/json`, без редиректов) с путём `/join/*` и идентификатором приложения (`TEAMID.bundleId` — сообщит iOS-разработчик);
- веб-страница `/join/<token>`: показывает «Вас приглашают в семью {familyName}» (данные из `GET /invitations/preview`), кнопку «Открыть в приложении» (кастомная схема `homefold://join/<token>`) и ссылку на App Store; токен в разметке и логах не светить;
- токен не должен попадать в access-логи (маскировать путь `/join/*`).

### 2.6 [P1, M] Аватары участников

Клиент даёт участнику загрузить фото профиля: свой — любой участник, чужой — администратор (в том числе для приглашённого, который ещё не вошёл). Клиент отправляет **квадратный JPEG ~320×320, до 512 КБ**.

- `PUT /families/me/members/{userId}/avatar` — тело: `image/jpeg`, ≤ 512 КБ; проверка сигнатуры JPEG и размера; права: сам участник или админ (иначе `403`). Для ожидающего приглашения — `PUT /invitations/{id}/avatar` (при принятии переносится участнику).
- `DELETE` по тем же путям — удалить фото.
- В `GET /families/me` у участника поле `avatarUrl` (подписанная ссылка на 1 час или бессрочный URL за CDN с неугадываемым ключом — на выбор разработчика) и `avatarVersion` (int, растёт при смене).
- Событие `Change` сущности `family`, чтобы остальные участники подтянули новый аватар.
- Хранить в том же объектном хранилище, что и документы, отдельным префиксом; при удалении участника/аккаунта удалять объект.
- Это **не** документ: не считается в лимите файлов и объёма.

### 2.7 [P1, S] Настройки уведомлений: согласовать с клиентом

`GET|PUT /settings` уже есть. Что добавить и уточнить:
- `defaultReminderMinutes` (`0 | 10 | 30 | 60 | 1440`, по умолчанию `30`) — напоминание по умолчанию для новых дел; хранится на сервере, чтобы совпадало на всех устройствах пользователя;
- `timezone` (IANA) клиент шлёт при каждом входе и при смене часового пояса (`NSSystemTimeZoneDidChange`);
- **Политика тихих часов.** Клиент переносит локальное напоминание на **конец** тихого окна, а если после переноса оно опоздало бы к сроку — не показывает. Серверный push сейчас при тихих часах **просто не отправляется**. Привести к одной логике: отложить отправку до конца окна (с `apns-expiration` = срок дела для напоминаний; для push о назначении — до конца окна, но не дольше 12 часов), либо согласовать иное с продуктом. Эти правила одинаково работают для `taskReminders` и `shoppingPush`.

### 2.8 [P1, M] Push-уведомления для мобильного клиента

Сейчас есть только alert-push при назначении дела или покупки. Нужно:
1. **Тихий push для синхронизации** (`apns-push-type: background`, `content-available: 1`, без звука, `apns-priority: 5`) при появлении изменений в семье — чтобы клиент в фоне вызвал `/sync/pull`. Объединять частые изменения (не чаще раза в 30 секунд на устройство).
2. Единый формат payload: `aps.alert{title, body}`, `kind` (`task | shopping | family | sync`), `entityId`, и `deeplink` (`homefold://task/<id>`, `homefold://shopping`, `homefold://family`) — клиент по нему открывает экран.
3. `apns-collapse-id` по сущности, чтобы повторные уведомления о том же деле не копились.
4. Удалять токен устройства при ответе APNs `410 Unregistered` / `BadDeviceToken`.
5. Тексты на русском, с правильными формами (имя назначившего: «Анна назначила вам дело»). Сейчас в тексте нет, кто назначил — добавить.
6. Новое событие (P2): «Участник присоединился к семье» — админу.
7. Не отправлять push самому автору изменения (уже так для назначений — проверить для остальных).

### 2.9 [P0, S — документ] Соответствие полей клиента и сервера

Решение: **эталон — сервер**, клиент сам переводит поля при отправке и получении. Backend ничего не переименовывает, но разработчик должен знать таблицу соответствия (клиент → сервер):

| Сущность | Клиент (локально) | Сервер |
|---|---|---|
| shoppingList | `title`, `isArchived` | `name`, `status: active/archived`, `archivedAt` |
| shoppingItem | `isBought` | `purchased`, `purchasedById`, `purchasedAt` |
| taskSeries | `recurrence` (`none/daily/weekly/monthly`), `startDate: Date`, `hasTime`, `checklistTemplate` | `repeat`, `startDate: "YYYY-MM-DD"`, `time: "HH:mm"?` + `timezone`, `checklist: string[]` |
| taskOccurrence | `dueAt: Date`, `hasTime`, `isDetached` | `date` + `time?` + `timezone`, `overridden` |
| checklistItem | `isDone` | `done` |
| member | `toneIndex` (0–3) | `color` (0–7); клиент использует `color % 4` |

Дата и время: клиент всегда отправляет `timezone` (IANA, часовой пояс семьи на момент создания дела); сервер считает повторы и сроки напоминаний в этом поясе.

### 2.10 [P0, M] Подписки: что нужно от сервера

Клиент (StoreKit 2) покупает, получает подписанную транзакцию (JWS) и отправляет её на `POST /billing/verify`. Тариф семьи ставит только администратор; решение о тарифе всегда за сервером (клиент временно ставит локальный Plus и откатывает его, если `verify` не прошёл).

Требования:
- `POST /billing/verify` идемпотентен (повтор той же транзакции → 200 с тем же состоянием); принимать JWS по цепочке сертификатов Apple (корневой сертификат уже в `backend/certs`); проверять `bundleId`, `environment`, `productId ∈ APPLE_PRODUCT_IDS`;
- привязка подписки к **семье** (`originalTransactionId` ↔ `familyId`), как сейчас (`SUBSCRIPTION_BOUND_TO_OTHER_FAMILY`). Клиент будет передавать `appAccountToken = UUID семьи` при покупке — читать его из транзакции и сверять с семьёй, если он есть;
- после изменения тарифа: `Change` для сущности `family` (клиент перечитает `GET /families/me` → `plan`) и тихий push;
- вебхук Apple (Server Notifications V2): обработать как минимум `SUBSCRIBED`, `DID_RENEW`, `DID_CHANGE_RENEWAL_STATUS`, `EXPIRED`, `GRACE_PERIOD_EXPIRED`, `REFUND`, `REVOKE`; период **grace period** считается активной подпиской; идемпотентность по `notificationUUID`;
- `GET /billing/status` отдаёт: `premium`, `plan`, `productId`, `expiresAt`, `willRenew`, `inGracePeriod`, `limits`, `purchasedBy` (userId администратора) — клиент показывает статус в настройках;
- **Что делать, когда подписка кончилась** — продуктовое решение (раздел 4), предложение: ничего не удалять; свыше лимита — «только чтение»: нельзя добавить участника, файл, повторяющееся дело; существующие серии перестают материализовать новые выполнения, но уже созданные остаются; документы сверх лимита остаются доступными для просмотра и удаления;
- продукты: `app.ryadom.plus.monthly`, `app.ryadom.plus.yearly` (по умолчанию в `APPLE_PRODUCT_IDS`). Настроить в App Store Connect, получить ключ App Store Server API (для `getTransaction`).

### 2.11 [P0, S] Удаление аккаунта и данных

Требование App Store (5.1.1(v)). `DELETE /account` уже есть — проверить полноту:
- удаляет пользователя, его сессии, токены устройств, настройки;
- удаляет **файлы** документов автора и аватар в хранилище (не только записи);
- последний администратор семьи с другими участниками → `409 LAST_ADMIN` (клиент покажет, что делать); если участник один — удаляется вся семья со всеми данными;
- события `Change` для остальных участников семьи (`family`), чтобы клиенты убрали пользователя;
- документирован срок физического удаления из бэкапов.

### 2.12 [P1, S] Вход для ревью App Store

Ревьюеру нужен рабочий вход без своей почты. Предложение: одна тестовая учётка (email в конфиге `REVIEW_EMAIL`, фиксированный код `REVIEW_CODE` из секретов) только в окружении `production`, с отдельной демо-семьёй. Это осознанное исключение из безопасности — включается переменной окружения, логируется, код не публикуется в репозитории.

### 2.13 [P1, M] Надёжность синхронизации

- `/sync/push`: ограничить размер тела (например, 1 МБ) и размер `payload` одной операции; вернуть `413` с понятным кодом;
- `/sync/pull`: сохраняемость курсора — клиент не должен терять изменения при переносе семьи между инстансами; курсор монотонный и не зависит от инстанса;
- WebSocket: при более чем одном инстансе рассылать `changed` через Redis pub/sub (или аналог), иначе устройство на втором инстансе не получит сигнал;
- `Change`-журнал: политика очистки (хранить ≥ 90 дней); клиент, чей курсор старше, получает `410 CURSOR_EXPIRED` и делает полную загрузку (`GET /sync/snapshot` или набор `GET` по сущностям — вопрос к разработчику, предложить вариант);
- серверное время (`serverTime`) использовать клиентом для сдвига часов — убедиться, что отдаётся.

### 2.14 [P1, M] Безопасность и персональные данные

- Все личные данные только по HTTPS; HSTS; строгие CORS (веб не нужен — отключить);
- лимиты запросов уже есть для входа — добавить общие лимиты на пользователя и на IP, отдельные — на загрузки и на `/invitations/preview`;
- токены, коды, JWS не писать в логи; журнал аудита для действий администратора (удаление участника, смена роли, подписка);
- документы: шифрование на стороне хранилища (SSE), подписанные ссылки 120 с (уже), опционально антивирусная проверка загрузок;
- **Хранение данных.** Если целевая аудитория — граждане РФ, персональные данные должны храниться на серверах в РФ (152-ФЗ). Это влияет на выбор хостинга и объектного хранилища — **решить до выбора инфраструктуры** (раздел 4).

### 2.15 [P1, M] Окружения, развёртывание, эксплуатация

- Окружения `dev` / `stage` / `prod`; секреты — из менеджера секретов, не из репозитория; `.env.example` актуален;
- Docker-образ (есть Dockerfile), `prisma migrate deploy` при выкладке, миграции обратно совместимы (клиенты в магазине живут месяцами);
- CI: линт, сборка, 98+ тестов, проверка актуальности `openapi.json`, запуск миграций на чистой БД;
- мониторинг: `/health` (есть) + метрики (RPS, латентность, ошибки), Sentry или аналог, алерты на 5xx и на очередь push;
- резервные копии PostgreSQL ежедневно, проверка восстановления;
- почта: SPF/DKIM/DMARC для домена отправителя; сейчас `MAIL_FROM = HomeFold <no-reply@ryadom.app>` — заменить на домен продукта; шаблон письма с кодом уже на русском;
- версионирование API: **ввести префикс `/v1`** до первого релиза клиента (после выхода менять пути будет дорого).

## 3. Порядок работ

1. **Этап 1 — разблокировать клиента (P0):** 2.2 → 2.1 → 2.3 → 2.4 → 2.9 → 2.11. После него iOS может подключить вход, семью, покупки, дела и документы.
